# PRD — Disseqt UC1: Reconciliation & Anomaly Detection Agent

_v1 · Sep 2026 · Owner: Ankit Kumar · Consumers: coding agents (Claude Code primary) + owner comprehension gates. Interview submission for Disseqt AI (FDE role, Mortgage Capital PoC brief). Built from scratch; a prior reference implementation exists but is NOT to be copied — this build is fresh._

---

## 1. Problem Statement

Mortgage Capital's operations team reconciles three monthly artifacts — a servicing extract, a payments file, and an investor report — by hand. Discrepancies (missed payments, duplicate direct debits, charged-rate breaches of contractual margin) are found late, explained inconsistently, and remediated without a clean audit trail. An LLM could accelerate mapping, classification, and explanation, but an unsupervised LLM in a financial reconciliation path is unacceptable: hallucinated numbers, invented exception types, and unreviewed prose reaching analysts are dealbreakers. The exercise (and Disseqt's product thesis) demands an agent where deterministic code owns all numerical work, humans gate the critical step, and every LLM output is validated before an analyst sees it — with the whole run instrumented so the evidence exists in Disseqt's dashboard, not in claims.

## 2. Goals

1. **Working end-to-end agent**: ingest → mapping proposal → human confirmation → deterministic reconciliation → constrained classification + drafted rationale → validation → PASS log / BLOCK-held — runnable in one command, zero credentials required.
2. **Provable correctness**: the deterministic engine scores recall 1.0 / 0 false positives against a seeded ground-truth answer key generated by this repo (this also answers the brief's open question about sample data).
3. **Validation that demonstrably works**: every validator has a test that drives it to FAIL; a poisoned-rationale scenario shows BLOCK holding output from the analyst.
4. **Real Disseqt instrumentation path**: typed spans emitted per their documented wire protocol; live mode = env vars only; mock transport otherwise.
5. **Owner defensibility**: the owner can explain every design decision to a CTO — enforced by per-milestone comprehension gates (see §9).

## 3. Non-Goals

- **No production or real loan data** — synthetic only, per the brief ("no production loan book"). Anonymised generation with seeded errors.
- **No LLM participation in matching/netting/comparison** — not even as a fallback. The brief's parenthetical "(deterministic engine, not the LLM)" is a hard boundary, not guidance.
- **No dashboard UI build** — analytics ship as JSON endpoints; Disseqt's dashboard is the visualization story. A UI would compete with the product we're demonstrating.
- **No UC2 implementation** — the walkthrough carries a mapping appendix showing how UC2's three EU AI Act controls are evidenced by spans this build already emits; building UC2 would violate the brief's "pick one."
- **No retry queues / persistence beyond JSONL+in-memory** — PoC-sized on purpose; a database is premature and adds interview surface without value.
- **No Node.js sidecar for the SDK** — their SDK is Node-only; we integrate via the documented wire protocol from Python (see R6). Cleaner, and itself an FDE judgment call to present.

## 4. User Stories (priority order)

- As a **reconciliation analyst**, I want discrepancies found by code and explained in plain English with every number traceable to a source row, so that I can act without re-verifying arithmetic.
- As a **reconciliation analyst**, I want to confirm (or correct) the proposed column mapping before anything runs, so that a wrong mapping can never silently produce wrong reconciliation.
- As a **reconciliation analyst**, I want unreliable AI-drafted explanations held for review rather than shown as fact, so that I never remediate against a hallucination.
- As an **operations lead**, I want a remediation log with owner, priority, evidence, and audit trail per exception, so that follow-up is assignable and auditable.
- As an **operations lead**, I want run analytics (PASS/BLOCK rates, validator scores, latency, token cost, drift vs a recorded Week-1 baseline), so that the PoC's value is measured, not asserted.
- As a **Disseqt reviewer (CTO/Lead Eng)**, I want every model call, tool call, and agent step visible as typed spans attributable to a registered application, so that the governance story is evidenced end to end.
- Edge: as an **analyst**, when an ingested file contains instruction-like text or PII, I want the run flagged before any LLM call consumes it.
- Edge: as an **analyst**, when the LLM is unavailable, I want deterministic results to still exist and the prose steps to fail honestly (held, labeled), never fabricated.

## 5. Requirements

### P0 — Must have

**R1 · Sample-data generator + answer key** — `data/generate_samples.py`
Generates `servicing_extract.csv`, `payments_file.csv`, `investor_report.csv` for N synthetic loans, deterministic under `--seed`. Seeds three error types (the closed exception set): `MISSING_PAYMENT`, `DUPLICATE_DIRECT_DEBIT`, `RATE_MARGIN_BREACH`. Writes `ground_truth.json`: `{seed, n_loans, seeded_exceptions: [{type, loan_id, detail}], exception_count}`. Raw headers deliberately differ per file (e.g. `LoanIdentifier` vs `loan_ref` vs `Loan_ID`) so mapping is a real task.
*Acceptance:* Given seed 42 and 40 loans, When generated twice, Then outputs are byte-identical; And every manifest entry is verifiable by hand in the CSVs; And no real-world PII patterns appear in generated values.

**R2 · Deterministic reconciliation engine** — `app/engine.py`
Pure functions; stdlib only. Canonical fields per file kind; `load_mapped(path, mapping)` applies a confirmed `{raw_header: canonical}` mapping. `reconcile(servicing, payments, investor) -> list[Exception_]` where `Exception_ = {ex_id, ex_type ∈ closed set, loan_id, detail, evidence: [verbatim source rows]}`. Detection: MISSING_PAYMENT (scheduled > 0, received == 0), DUPLICATE_DIRECT_DEBIT (>1 posting netting to an exact multiple of scheduled), RATE_MARGIN_BREACH (charged margin > contractual). `score_against_ground_truth(found, manifest)` returns precision/recall, per-type, and verbatim `missed`/`spurious` lists.
*Acceptance:* Given the seed-42 dataset, When the engine runs with the correct mapping, Then recall == 1.0 and false_positives == 0 against the manifest; And every exception carries ≥1 evidence row; And Given a wrong mapping (e.g. amounts column unmapped), Then the engine produces honestly wrong output surfaced by the score function — never a crash that hides it. No LLM import reachable from this module (import-graph test).

**R3 · LLM provider seam** — `app/providers.py`
`LLMProvider` interface with three ops: `propose_mapping(headers, canonical) -> dict`, `classify(detail, engine_type) -> {type, confidence}`, `draft_rationale(exception) -> str`. Two implementations: `OpenAIProvider` (customer key via env, JSON response_format, temperature 0, usage captured) and `MockProvider` (deterministic, alias-table mapping, agrees-with-engine classification at fixed confidence, template rationale quoting only evidence/engine facts). Selected by `LLM_PROVIDER=openai|mock`, default mock. **The mock never simulates judgment quality: all scores and verdicts downstream are computed by validators, never invented.**
*Acceptance:* Given no environment variables at all, When the full pipeline runs, Then it completes with computed validator scores; Given `LLM_PROVIDER=openai` + key, Then the same pipeline runs with real calls and captured token usage; And a parity test asserts both providers emit identical output *shapes*.

**R4 · Validators + realtime policy** — `app/validators.py`
Six validators, deterministic, each returning `(score, findings[])`:
- `faithfulness(rationale, evidence, engine_detail)`: every numeric value (compared as float, format-insensitive) and every loan id in prose must resolve to evidence rows OR the engine's own detail string (the engine is trusted computation; the LLM is not — prose may quote either, invent neither).
- `answer_relevance(rationale, ex_type, loan_id)`: prose references the exception's loan and its type's vocabulary.
- `classification_in_set(cls)`: out-of-set type scores 0.
- `plan_coherence(spans)`: `reconcile_engine` span exists and precedes any `draft_rationale` span.
- `injection_scan(rows)` / `pii_scan(rows)` on ingested data (instruction patterns; IBAN/email/phone patterns).
Policy: `apply_policy(scores, thresholds) -> PASS|BLOCK`; defaults block on a single ungrounded number. **BLOCK holds the exception for human review with its scores and findings — never discards, never shows.**
*Acceptance (each independently):* a test drives the validator below threshold with a realistic bad input (ungrounded number; foreign loan id; off-topic prose; invented type; draft-before-engine span order; injected instruction; embedded IBAN) — the guard is seen to fail before it is trusted. Plus: Given a provider that drafts a plausible fabricated payment instruction, When a full run executes, Then remediation_log is empty and all exceptions sit in held_for_review with verdict BLOCK.

**R5 · Agent graph + API** — `app/graph.py`, `app/main.py`
LangGraph state machine: `ingest (code; runs injection/PII scans) → propose_mapping (LLM) → INTERRUPT → reconcile (engine) → classify_and_draft (LLM) → validate+policy → emit`. The interrupt is structural: no code path reaches the engine without a confirmed mapping. FastAPI: `POST /runs` (start; returns run_id + proposed mapping; graph paused), `POST /runs/{id}/confirm` (human supplies/edits mapping; graph resumes), `GET /runs/{id}` (remediation_log + held_for_review + timings), `GET /runs/{id}/analytics` (span timeline, per-validator means, PASS/BLOCK counts, per-step latency, model calls, token total, est. cost, drift vs baseline), `POST /baseline` (record Week-1 manual-process metrics for drift).
*Acceptance:* Given a started run with no confirmation, Then no engine span exists and results are absent; Given confirmation, Then span order shows `mapping_confirmed` strictly before `reconcile_engine`; And the remediation log entries each carry `{ex_id, type, loan_id, rationale, owner, priority, evidence, scores, verdict}`.

**R6 · Disseqt wire client** — `app/disseqt_wire.py`
Python client speaking the SDK's documented protocol (SDK itself is Node-only): auth headers `X-API-Key` + `X-Project-Id`; agentic traces to the documented agentic-monitoring endpoint using their span vocabulary (AgentExec / model call / tool call, service_name, application attribution); optional validator calls to `POST /api/v1/sdk/validators/{domain}/{validator}`. Two transports behind one interface: `LiveTransport` (env: `DISSEQT_API_KEY`, `DISSEQT_PROJECT_ID`, optional endpoint overrides) and `LocalTransport` (JSONL to `traces/<run_id>.jsonl`, identical span payloads). The graph emits through this client exclusively.
*Acceptance:* Given no Disseqt env vars, When a run executes, Then the local trace contains the full typed span sequence (agent steps, every model call with usage, every tool call); Given env vars, Then the identical payloads go to the live endpoints (verified by a transport-level test with a captured fake server — no live call in the suite); And a parity test asserts both transports receive the same span sequence for the same run.

**R7 · Tests + gates** — `tests/`
Single command: `python3 -m unittest discover tests -v`. Covers: R1 determinism, R2 ground-truth score + evidence + import-graph, R3 parity + keyless run, R4 every-validator-seen-to-fail + poisoned-provider e2e, R5 checkpoint structural + span order, R6 transport parity. Suite green is the merge gate for every milestone.

**R8 · README + WALKTHROUGH** — repo root
README: quickstart (zero-credential), architecture diagram (ASCII), design decisions, layout. WALKTHROUGH: the CTO narrative — trust boundary, checkpoint realness, validators-seen-to-fail, honest limitations (what's mocked and why), suggested 6-minute demo order, and the UC2 appendix mapping Art 15/14/12 to spans this build emits.

## 9. Comprehension gates (process requirement, non-negotiable)

After each milestone the building agent STOPS and produces a plain-English brief: what this piece does, the 2–3 decisions that could have gone another way, and why they didn't. The owner answers three interrogation questions (posed by the reviewing assistant) before the next milestone dispatches. All briefs + answers accumulate in `docs/EXPLAIN_BACK.md` — that file is the owner's interview prep and ships in the repo as evidence of process. Optimize every implementation choice for the owner's ability to defend it over cleverness; where two designs are equal, choose the one that explains in one sentence.
